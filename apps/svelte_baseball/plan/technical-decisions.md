# Technical Decisions

## 採用技術

### Vite

採用理由:

- 静的配信用のフロントエンド構成を素直に作りやすい
- 開発サーバーと本番ビルドの流れが明快
- ビルド成果物を `dist/` にまとめやすい

### Svelte

採用理由:

- 小規模な SPA をシンプルに構成しやすい
- UI コンポーネントと状態の対応が分かりやすい
- MVP では過度な抽象化なしで画面を組み立てやすい

### TypeScript

採用理由:

- ゲーム状態、結果カテゴリ、進塁処理を型で整理しやすい
- 将来的な仕様追加時に破綻しにくい
- UI とゲームロジックの境界を明確にしやすい

## 採用しないもの

### ルーティングライブラリ

今回は単一画面の SPA のため不要です。
画面遷移を前提にしないことで、初期構成を軽く保ちます。

### 外部状態管理ライブラリ

初期段階では不要です。
まずは Svelte の標準機能と、TypeScript の純粋なロジックモジュールで十分に扱えます。

### UI コンポーネントライブラリ

MVP では不要です。
ゲーム向けの小さな UI を自前で組む方が、依存関係を抑えつつ見通しを保ちやすいです。

### Tailwind CSS

今回は採用しません。
画面数が少なく、スタイル要件も限定的なため、通常の CSS または Svelte コンポーネント内スタイルで十分です。

### SvelteKit

今回は採用しません。
サーバー機能やルーティングを必要としておらず、静的な単一 SPA としては Vite ベースの方が構成を単純にできます。

## 想定ディレクトリ方針

実装時は、おおむね次のような責務分離を想定します。

- `src/`
  - Svelte 側の画面と UI
- `src/lib/game/`
  - ゲーム状態、判定、進塁処理
- `src/lib/config/`
  - コース定義、確率設定
- `src/lib/types/`
  - 型定義

最初から過度に細分化せず、責務が増えた段階で分割を進めます。

## ロジック設計方針

- UI 層は「入力を受けて状態を表示する」ことに集中させる
- 判定ロジックは純粋関数寄りに切り出し、後から調整しやすくする
- 乱数処理は一か所に寄せ、結果の決定経路を追いやすくする
- コース別の確率テーブルは設定データとして管理し、将来は差し替え可能にする

## 永続化の扱い

MVP ではローカル保存を入れません。
再プレイ前提とし、まずは 1 回ごとのゲーム体験を成立させます。

## テスト方針

初期実装では、まずゲームロジックの分離を優先します。
ロジックが安定した段階で、必要に応じて `Vitest` などによる判定ロジックのテスト追加を検討します。
